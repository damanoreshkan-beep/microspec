# ax56 — "bring a Wi-Fi 6 chip to life" (research + build blueprint)

A farm PWA around the ASUS USB-AX56 (Realtek RTL8852AU). Companion to the native driver
(github.com/damanoreshkan-beep/rtl8852au-userspace). **Play/create, not a passive readout**: the viewer
reads a mode-switched adapter's live registers and replays the chip's cold-to-firmware bring-up, stage by
stage, on a glowing register lattice.

## The story is SOLVED now (updated 2026-08-24 — supersedes the old "wall" ending)

The blueprint originally ended on the `H2C_PATH_RDY` wall, because that was where the port stopped. The
companion driver has since taken the **full** no-root userspace bring-up all the way through: firmware
download to `STS = 7 BOOTED`, live 802.11 monitor capture, radiotap + RSSI, and channel hopping. So the app
tells the true, finished story — cold chip → firmware running — not a dead end. The last stage is the
milestone, not a wall.

- VALIDATED (driver repo, this project): the six-stage sequence below runs on real silicon; `WCPU_FW_CTRL`
  goes `0x1` (FWDL_EN) → `0x23` (H2C_PATH_RDY armed) → `0x27` (FWDL_PATH_RDY) → `0xe2` (FWDL_STS[7:5] == 7,
  booted). Source: driver `hwdriver.c` run logs, `docs/RESEARCH.md`.

## The hard constraint (settles the concept — unchanged)

A farm PWA **cannot control** this adapter to completion: WebUSB blocks the mass-storage class, so the
storage→wifi mode-switch is impossible in a browser, and there is no usbfs `DISCONNECT_CLAIM`; firmware
download also needs Realtek's blob, which the public farm does not redistribute. So the app is a
**viewer/explorer of an already-switched adapter** plus a full **demo** that needs no hardware and replays
the solved bring-up. What a PWA CAN do (proven by `hackrf.js` / `rtlsdr.js`): claim a vendor-class device and
issue vendor control transfers — exactly our register read.

## WebUSB register read — the VERIFIED control transfer (corrects the old note)

The rtw89 vendor register access encodes the address across BOTH setup fields — the old blueprint's
`value: addr, index: 0` is **wrong** for any address above `0xFFFF` and is only accidentally right for the low
page. Verified encoding (driver `hwdriver.c` `r32()`): request `0x05`, **`wValue = addr & 0xFFFF`,
`wIndex = (addr >> 16) & 0xFF`**, read 4 bytes little-endian.

```js
const r = await dev.controlTransferIn(
  { requestType: "vendor", recipient: "device", request: 0x05, value: addr & 0xffff, index: (addr >> 16) & 0xff }, 4);
const v = (r.status === "ok" && r.data && r.data.byteLength >= 4) ? r.data.getUint32(0, true) >>> 0 : 0xdeadbeef;
```

Lifecycle is plain WebUSB in the view (no DSP worker, unlike the five `usbsession` apps):
`requestDevice({ filters:[{vendorId:0x0b05,productId:0x1997}] })` → `open()` → `selectConfiguration(1)` →
`claimInterface(0)`. Storage mode `0bda:1a2b` is intentionally NOT offered — the app tells the user to switch
first (links the driver repo); demo meanwhile. Pure logic (decode, stages, demo) stays in
`packages/runtime/ax56.js` (unit-tested browser-free); the control transfer is the only WebUSB in the view.

## The six bring-up stages (each a real register check the driver uses)

1. **power-on** — `R_AX_PLATFORM_ENABLE 0x0088` PLATFORM_EN bit0 (MAC powered).
2. **DMAC** — `R_AX_DMAC_FUNC_EN 0x8400` DMAC_FUNC_EN bit29.
3. **DLE(DLFW)** — `R_AX_WDE_INI 0x8D00` & `R_AX_PLE_INI 0x9100` low bits == 0x3 (init-ready).
4. **HCI DMA** — `R_AX_HCI_FUNC_EN 0x8380` TX/RX DMA bits [1:0] == 0x3.
5. **CPU / H2C** — `R_AX_WCPU_FW_CTRL 0x1E0` H2C_PATH_RDY bit1 arms (the old "wall", now open).
6. **firmware booted** — `R_AX_WCPU_FW_CTRL 0x1E0` FWDL_STS `(v>>5)&7 == 7` (WCPU_FW_INIT_RDY).

`R_AX_SYS_CFG1 0x00F0` → `cut = (v>>12)&0xf` (measured 2 = C-cut). The low page `0x0000–0x00FC` (64 u32,
measured on the real C-cut chip, `DEMO_LOW_PAGE`) is the register lattice. Unmapped reads answer
`0xdeadbeef` — an honest "no chip there" tell and a dark cell.

## The experience (design — premium, farm taste)

- One `#view`, `fit: true` single screen, kit surfaces, neumorphic `sf-*`, Geist, theme-aware, no emoji,
  no spinners, lucide only.
- **Register lattice** (canvas, the "wow"): the low page as an 8×8 grid; each cell's glow = value activity
  (popcount-weighted), `0xdeadbeef` cells stay dark. On connect / each demo frame, values ripple in.
  Theme-aware colours read from `data-theme` (canvas can't use DaisyUI vars), sized from its box (DPR),
  the `useCanvas` idiom from `gsmscan`.
- **Stage stepper**: the six stages as a compact connected rail; each node lights (`--app-accent` mark) when
  its register check passes. The active stage's key register shown as a live mono hex readout.
- **On real hardware** the app reads the live low page + the six registers once: a freshly mode-switched
  cold chip lights **power-on + cut** and the lattice fills with real values — the rest of the rail is
  honestly "not run" (the PWA does not drive the init; the native driver does). **Demo** replays all six
  stages to BOOTED so the full story is alive without hardware and the Chromium/axe gate sees a populated
  screen.
- Pinned status island: chip cut, connection, a demo step/replay control, disconnect.

## Honesty gates specific to this app

- Never imply the PWA switches modes or downloads firmware — it reads a pre-switched chip; the demo is
  labelled and a real connect replaces it. The native driver is where the full bring-up runs; link it.
- `0xdeadbeef` cells are shown truthfully as dark. The story is the real, now-finished bring-up.

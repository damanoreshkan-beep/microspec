# Background execution — what can run when the app is not open

Research pass, 2026-08-03. Question: how do we make a farm app do work while it is closed —
notifications, scheduled jobs, a local server — and what does the **APK** route unlock that the
browser does not.

Every claim is labelled **VERIFIED** (checked against a primary source this session),
**KNOWN** (well-established, not re-checked here), or **UNKNOWN** (must be measured before we build on it).

---

## 0. The premise to kill first: a service worker is not a server

**KNOWN.** A service worker has **no socket, no port, no process of its own**. It is an event
handler the browser starts on demand (`fetch`, `push`, `sync`, `notificationclick`), runs for a few
seconds, and kills. Nothing outside the browser can connect to it; it cannot listen; it cannot wake
itself on a timer.

What *feels* like "the SW spun up a server" is its `fetch` handler answering requests for its own
scope with a synthesized `Response` — the page asks for `/api/x`, the SW replies from cache or from
generated bytes, and DevTools shows a normal HTTP round-trip that never touched the network. That is
the whole trick behind "run a dev server in the browser" products (StackBlitz WebContainers): a SW
answering fetches for a virtual origin, plus WASM doing the compute. Still no listening socket.

So: **"the app is closed but still works" is never the SW deciding to run.** Something external must
wake it — a push message, a connectivity change, a browser-scheduled sync — or, in an APK, a real OS
process.

## 1. What can actually wake code with the app closed

### In an installed PWA (Chrome / Android)

| Mechanism | Wakes when closed? | Needs a server? | Reality check |
|---|---|---|---|
| **Web Push** (Push API + VAPID) | **Yes** — OS delivers, browser is launched to handle it | **Yes** — a push sender | The only *dependable* one. VERIFIED: `PushManager` supported in Chrome Android; delivery works with browser/app closed. Chrome enforces `userVisibleOnly: true` → **every push must show a notification**; no silent background work (KNOWN). |
| **Background Sync** (one-shot) | On regaining connectivity | No | Fires a deferred action after network returns. Not a scheduler. |
| **Periodic Background Sync** | Sometimes | No | VERIFIED: Chrome-only, requires **installed** PWA + permission, **~12 h floor**, and is engagement-gated — the browser decides. Fine for "refresh the cache eventually", useless for "notify me at 08:00". |
| **Background Fetch** | Yes, for transfers | No | VERIFIED: large downloads survive closing the browser, with an OS progress notification. Good for offline packs / media, not for logic. |
| **Notification Triggers** (`TimestampTrigger`) | — | — | **DEAD.** VERIFIED: Chrome ran two origin trials (80–83, 86–88) and **ended development**; never shipped. This is the API that would have given us local, server-free scheduled alarms. Its absence is the single biggest reason to care about the APK route. |

**Consequence:** in the browser, *any* "tell me later / tell me when X happens" feature requires
**our edge to hold the schedule and send a push**. There is no offline, device-local alarm on the web.

### In our current APK (`microspec-edge/template`, plain WebView shell)

**VERIFIED (MDN browser-compat-data, `main`):**

- `api.PushManager` → `webview_android: false`
- `api.Notification` → `webview_android: false` (crbug 40443309)
- `api.ServiceWorkerRegistration` → supported (mirrors Chrome)

So today the shell **regresses**: SW/offline works, but a farm app wrapped by apkforge **cannot show a
notification at all** — it is strictly weaker than the same app installed from Chrome. Anything
notification-shaped in an APK must come from **native code**, not from the page.

## 2. The two APK routes

### Route A — TWA (Trusted Web Activity): Chrome renders, we just ship the icon

The app runs in a real Chrome tab without chrome, so **all web capabilities survive** — Push,
notifications, everything the installed PWA has. androidx.browser also provides
`TrustedWebActivityService` **notification delegation** (web notifications are posted by *our* app,
under our icon and channel).

Cost / constraints (INFERRED unless noted — verify before building):

- **`/.well-known/assetlinks.json` at the DOMAIN root** (VERIFIED requirement). Our farm lives at
  `damanoreshkan-beep.github.io/microspec/` → the file must sit on the **user site**
  (`damanoreshkan-beep.github.io/.well-known/…`), i.e. a separate `damanoreshkan-beep.github.io`
  repo, or the farm moves to a custom domain. Without verification the APK still works but shows a
  Custom-Tab URL bar.
- Needs `androidx.browser` → the template stops being zero-dependency, and the APK stops being tiny.
- Needs Chrome installed and current on the device (fine for the S25).
- Notification delegation on Android 13+ needs `POST_NOTIFICATIONS` handling in the shell.
- Our **pure-Deno patcher** still works (it only rewrites `assets/`, `res/*.png`, `resources.arsc`),
  but a TWA carries the verified origin **inside `resources.arsc`/manifest** — patching a *start URL*
  per request is fine only if all generated APKs share one verified origin. **Arbitrary-URL apkforge
  and TWA are incompatible** — arbitrary URLs can never be verified.

### Route B — native shell: keep the WebView, add real Android capabilities

Add to the template (Java, still zero-AndroidX possible), exposed to the page over a
`@JavascriptInterface` bridge:

- **Native notifications** — `NotificationManager` + channel. Works with the WebView closed if posted
  from a service/receiver.
- **Scheduling** — `AlarmManager` (exact-ish, device-local, survives reboot with a
  `BOOT_COMPLETED` receiver) or `WorkManager`-style periodic work (~15 min floor, Doze-batched).
  **This is the capability the web cannot give us at all.**
- **Foreground service** — a persistent notification buys a long-running process: background audio,
  sensor logging (GSM/LoRa/HackRF scans with the screen off), a socket that stays up.
- **Local HTTP server** — `ServerSocket` in ~200 lines, no deps.

**Why `targetSdk 29` is a gift here (VERIFIED):**

- `foregroundServiceType` is mandatory only for **targetSdk ≥ 34** → our services need no type
  declaration and dodge the Android 14/15 FGS-type tightening.
- `POST_NOTIFICATIONS` is a runtime permission only for **targetSdk ≥ 33**; legacy-target apps are
  temporarily granted until the user decides.
- The sideload floor stayed at **targetSdk 24 through Android 14, 15 and 16** (`INSTALL_FAILED_DEPRECATED_SDK_VERSION`
  below that) — 29 remains installable. The API-36 deadline (2026-08-31) is a **Google Play** rule and
  does not touch us; we never publish.

**UNKNOWN / must check before building:** `SCHEDULE_EXACT_ALARM` behaviour for a legacy-target app on
Android 15/16; Doze batching of our alarms on One UI (Samsung is aggressive); whether Samsung's
"put unused apps to sleep" kills a legacy-target FGS.

## 3. The local-server question

Two different things get called "run a server locally", and only one of them needs a socket.

1. **Serve the app to itself, offline.** No socket needed. `shouldInterceptRequest` on a synthetic
   `https://…` host answers from `assets/` — the scheme is `https`, so it is a **secure context** and
   SW/sensors/camera all work. This is exactly what androidx `WebViewAssetLoader` does
   (`https://appassets.androidplatform.net`); we can hand-roll it in ~60 lines and stay AndroidX-free.
2. **Serve to *other devices*.** A real `ServerSocket` — phone becomes a station on the LAN: push a
   file from the laptop, drive a farm app from a second screen, expose the sensor stream. This is the
   only reason to open a port, and it is a genuinely new product surface, not an optimisation.

**Secure-context rule (VERIFIED):** loopback is trusted — Android's own docs call `localhost` "the
trusted hostname", while a non-loopback IP such as `10.0.2.2` is **not** a secure context in WebView
and silently disables Service Workers, geolocation, camera and mic. So a local server must be reached
as `http://localhost:PORT`, never as the LAN IP, if the page needs secure-context APIs.

## 4. What this means for the farm

The pieces we already have: an **edge** (two Deno processes on the VPS, private repo), a signed-APK
pipeline, `packages/runtime/permissions.js` with a `notifications` entry that nothing uses yet, and
zero push infrastructure anywhere in the farm (VERIFIED by graph search: no `showNotification`,
`pushManager` or `periodicSync` call sites).

**A systemic "Alerts" capability is the high-value move, and it is a browser feature, not an APK
feature.** Edge holds the subscription + the rule, edge cron evaluates, edge sends a Web Push, the
runtime SW shows it. That lights up *every* app at once — price levels (btcflow/rates), ISS passes,
quakes, aurora/kp, launches, GitHub events (nova), habit reminders — and needs no APK at all.

Deno path for the sender: **`jsr:@negrel/webpush`** (RFC 8291/8292, `aes128gcm`, built on WebCrypto —
VERIFIED), or hand-rolled the way we hand-rolled JAR signing.

New state we would be taking on: a subscription store on edge (endpoint + keys per device) and
per-user rules — the first genuinely *stateful* thing the edge would own. That is a design decision,
not a detail.

**The APK route is worth it for what the browser structurally cannot do:** device-local alarms with
no network and no server, background sensor logging with the screen off, and a LAN-facing server.
Note the ordering trap: ship Alerts first and apkforge-generated APKs get *nothing*, because a
plain WebView cannot show a notification.

## Decision log

- Notification Triggers is dead → no server-free scheduled notification on the web. Closed.
- apkforge's WebView shell cannot show notifications today; a native bridge or TWA is required. Closed.
- TWA is incompatible with apkforge's arbitrary-URL promise (asset-links verification is per-origin);
  if we adopt TWA it is a **second, farm-only** APK flavour, not a replacement. Closed.
- Local asset serving does **not** need a socket; only cross-device serving does. Closed.

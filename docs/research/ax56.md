# ax56 — "bring a Wi-Fi 6 chip to life" (research + build blueprint)

A farm PWA around the ASUS USB-AX56 (Realtek RTL8852AU). Companion to the native driver
(github.com/damanoreshkan-beep/rtl8852au-userspace). **Play/create, not a passive readout**: the viewer
walks the chip's power-on → DMAC → DLE bring-up step by step and sees REAL register values light up.

## The hard constraint (settles the concept)
A farm PWA **cannot control** this adapter: WebUSB blocks the mass-storage class, so the storage→wifi
mode-switch is impossible in a browser, and there is no usbfs `DISCONNECT_CLAIM`. So the app is a
**viewer/explorer of an already-switched adapter**, plus a full **demo mode** that needs no hardware.
What a PWA CAN do (proven by the farm's `hackrf.js` / `rtlsdr.js`): claim a vendor-class device and issue
vendor control transfers. That is exactly our register read.

## WebUSB feasibility — confirmed, reuse the farm pattern
- Lifecycle: `createUsbSession` (`/_rt/usbsession.js`) — connect/claim/teardown, `$connected`/`$usbOk`.
  Five farm apps use it (fmradio, gsmscan, lorawatch, ether, subclone). It manages the granted `device`.
- Register read = a vendor control transfer, same shape as `hackrf.js:_in`:
  `dev.controlTransferIn({ requestType:'vendor', recipient:'device', request:0x05, value:addr, index:0 }, 4)`
  → LE u32. (rtw89 vendor reg access; addr in wValue, ≤0xFFFF.) Write = `controlTransferOut(..., 0x40-side)`.
- Filter: `{ vendorId:0x0b05, productId:0x1997 }` (wifi mode). Storage `0bda:1a2b` is intentionally NOT
  offered — the app tells the user to switch first (link to the driver repo), demo mode meanwhile.
- New runtime helper `/_rt/ax56.js` (mirrors hackrf.js/rtlsdr.js): `readReg32(dev, addr)`, `readCut(dev)`,
  the register map, the stage checks, and the demo dataset. Math/helpers here so `packages/runtime/tests`
  can unit-test them browser-free (register decode, stage predicates, demo generator).

## What we read (the register map — measured on real silicon this project)
- `R_AX_SYS_CFG1 0x00F0` → `cut = (v>>12)&0xf` (measured 2 = C-cut). Low page 0x0000–0x00FF is a live grid.
- Bring-up stages, each a real register check the driver uses:
  1. **power-on**: `R_AX_IC_PWR_STATE` / the 0x0005/0x0006/0x0088 dance — MAC powered.
  2. **DMAC**: `R_AX_DMAC_FUNC_EN 0x8400` bits (MAC/DMAC/DISPATCHER/PKT_BUF).
  3. **DLE(DLFW)**: `R_AX_WDE_INI_STATUS 0x8D00` / `R_AX_PLE_INI_STATUS 0x9100` == 0x3 (init-ready).
  4. **HCI DMA**: `R_AX_HCI_FUNC_EN 0x8380` TX/RX DMA.
  5. **CPU / fw**: `R_AX_WCPU_FW_CTRL 0x1E0` — FWDL_EN, and the **H2C_PATH_RDY wall** (bit1) this project hit.
- Unmapped reads answer `0xdeadbeef` — a great visual "no chip there" tell, and honest.

## The experience (design direction — cinematic, farm taste)
- One `#view`, single scroll, kit surfaces (`/_rt/ui.js` Island/Segmented), theme-aware, no emoji, no spinners.
- A **stage rail**: 5 stages as a vertical flow; each lights when its register check passes (green on real
  hardware, or stepped through in demo). The current register(s) for a stage shown as a live hex readout.
- A **register lattice** (WebGL, `/_rt/glstage.js` twin of hero): the low page as a grid of cells whose
  glow = value activity; `0xdeadbeef` cells stay dark. On connect, real values ripple in. This is the "wow".
- Honest ending: stage 5 shows the **H2C_PATH_RDY** cell NOT lighting — the real wall we found — with a
  one-line note linking the driver repo's STATUS. The app tells a true story, not a fake success.
- Demo mode (no device / desktop / gate): a scripted register stream drives the same visuals so the app is
  fully alive without hardware (and so the Chromium/axe gate sees the populated screen).

## Files (spec + adapter, farm contract)
```
apps/ax56/spec.json      tabs: [ {type:tool, view:ax56View, needs:['usb']}, {type:profile} ]; theme "signal"
apps/ax56/view.js        ax56View({S,...}) — stage rail + register lattice + connect/demo
apps/ax56/i18n/*.json    en, uk, ru, de, pl  (all 5 — farm i18n rule; include profile/install keys)
apps/ax56/{manifest.json, sw.js, brand.json, brand.svg, icon.svg, index.html, e2e.spec.mjs}
packages/runtime/ax56.js + packages/runtime/tests/ax56_test.js   register decode / stage / demo (unit-tested)
```
Register semantics come straight from the driver repo's docs/RESEARCH.md (already ours) — no new reversing.

## Build plan (one pass)
1. `/_rt/ax56.js` + unit test (decode, stages, demo) → `deno task test`.
2. spec.json + i18n (5) + manifest/sw/brand/icon/index.
3. view.js: stage rail + lattice + WebUSB connect (usbsession) + demo fallback.
4. Local gates (ajv+preflight+unit+counts+sw), then push → Chromium/axe verify, then the eye
   (`vps/eye.sh ax56` both themes) judged against DESIGN_RUBRIC.
5. Register in the launcher (deploy/manifest.mjs).

## Honesty gates specific to this app
- Never imply the PWA can switch modes or download firmware — it reads a pre-switched chip. Copy says so.
- The demo dataset must be labelled demo; a real connect replaces it. Don't dress demo values as live.
- `0xdeadbeef` and the H2C wall are shown truthfully — the app's story is the real bring-up, wall included.

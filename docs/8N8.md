# 8n8 — the pipeline, inside out

n8n gives you a canvas: a human draws the graph, the machine executes it. The graph precedes the work, and
everything the machine does was decided by a person in advance.

8n8 runs that backwards. **The agent does the work first. A run that proved itself freezes into a
deterministic node.** The graph is not drawn up front — it precipitates out of work that already succeeded.
Nobody sat down and designed `packages/gen/scaffold.mjs`; an agent hand-wrote `index.html`, `manifest.json`,
a service-worker stub and an icon for enough apps that the identical part became a function.

That is the whole idea, and it is falsifiable: if the pipeline's deterministic share does not go up over
time, 8n8 is not doing anything.

```bash
deno task 8n8 --list          # every node, script vs agent, and the determinism number
deno task gates               # the pre-push flow (10 nodes, concurrent)
deno task 8n8 gates --json    # machine-readable result
deno task 8n8 gates --dry     # print each node's argv, run nothing
deno task 8n8 author --app=x  # the per-app authoring flow
```

## The node

A node is `{ id, kind, phase, needs, scope, run, why, frozen }` in `tools/8n8/nodes.mjs`.

`kind` is the only field that matters to the thesis. **`script`** is a command: reproducible, no model, no
judgment. **`agent`** still needs a mind. `frozen` is the date a node stopped being an `agent` and became a
`script` — and it is one-way. A registry contract test fails if anything claims a freeze date without being
deterministic, and if the deterministic share ever drops below 60%.

At the time of writing: **17 script · 6 agent · 74% deterministic.**

## What may never freeze

Three nodes are permanently `agent`, and the reasons are not scheduling problems:

- **`ideate`** — a registry of app ideas is a registry of the past.
- **`research`** — freezing it would mean the farm already knows the API it has never met.
- **`taste`** — the eye. A gate that agrees with a bad screenshot is set too low, and the whole reason the
  farm keeps a human-grade visual pass is that every automated check was green when rave's transport read as
  one welded block. This node is the test that catches what the other nodes structurally cannot see.

`spec`, `i18n` and `view` are *partially* frozen and that is the interesting case: `packages/gen/authorless.mjs`
already emits a complete list-family app — spec, data adapter, both locales, brand — from a recipe, with no
LLM, and it passes the same ajv + preflight + Chromium gates as a hand-authored one. So the honest statement
is not "authoring cannot be frozen" but "authoring freezes one FAMILY at a time". Each new family that
freezes moves the number.

## Why the runner is not `&&`

`deno task gates` used to be nine commands joined by `&&`. Three concrete failures came out of that shape:

1. **A chain stops at the first red**, so one round answers one boolean and the next four failures stay
   hidden until you fix the first and run again. The runner executes every node whose dependencies are
   green and returns the **whole work list**.
2. **`deno task gates | grep …` returns grep's exit code**, not the gates'. That is how a red farm got
   pushed. The runner's exit code is the number of failed nodes, and it prints each failure with its node
   id, its argv and its output **in full** — never truncated, because a diagnostic you cut is a diagnostic
   you re-run.
3. **Independent checks had no reason to be sequential.** Measured on this device: 45.5s → 24.4s cold,
   16.3s warm, same checks plus one.

## A flow is a closed set, not a transitive closure

This was a real bug in the first version and it is worth stating, because the distinction is not obvious.

`needs` records the pipeline's **order**: `scaffold` precedes `preflight`, because when you are authoring an
app the boilerplate has to exist before it can be checked. But `gates` inspects a repo whose scaffold already
happened and is committed. Pulling dependencies in transitively dragged every gate back through the authoring
nodes and demanded `--app=<id>` for a whole-farm check.

So a flow names exactly what runs, and `needs` only *orders* it. A dependency outside the plan is treated as
already satisfied — it is history, not work. The registry test now asserts that no `gates` target is per-app,
so this cannot come back quietly.

## Adding a node

1. Add it to `NODES` with a real `why` — one line on what it buys, or for an agent node, what would have to
   become true for it to freeze.
2. If it is a `script`, `run` returns an **argv array**, never a shell string. Nodes are data, not text a
   shell re-interprets; that is why `globApps()` expands `apps/*` in JavaScript.
3. Put it in a flow. `deno test -A tools/8n8/run_test.js` (itself the `pipeline` node) checks the DAG is
   acyclic, every `needs` resolves, every script node produces a non-empty argv, and no agent node is
   pretending to be deterministic.

## Where it does not reach

`packages/gates/verify.mjs` — Chromium, axe, e2e, shots — is **CI-only**; this device may never run a
browser. The `ci` node reads the run-level conclusion of that workflow rather than re-implementing it, and
`shot` produces the pixels that `taste` then has to actually look at. 8n8 orchestrates the local pipeline
and reports on the remote one; it does not replace GitHub Actions.
